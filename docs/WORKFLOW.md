# WORKFLOW · 从意图到落地（vibecoding 规范）

> 适用范围：本项目所有「跟 AI 一起改设计 / 改代码」的工作。
> 运维细则（端口、重启、行为探针、进程排查、前端代理）见 [DEV_OPS.md](./DEV_OPS.md)，本文不重复。
> 落地日期：2026-09-14

---

## 0. 一句话

**每一轮只推进一个能验证的小步：AI 产出 → 你看 → 你拍板或改 → 记下来。**

原则：宁可多一轮确认，也不要一次改十个文件然后没人知道哪一步出的问题。

## 1. 四份东西，各管一段

| 文书 | 管什么 | 谁来写 | 稳定性 |
| --- | --- | --- | --- |
| `PLAN.md` | 要什么：做什么 / 不做什么 / 验收标准 | 人定方向，AI 可补细节 | 稳定，改动留痕 |
| 任务看板 | 怎么落地：任务、依赖、负责人 | AI 拆，人调整 | 随时可重建 |
| `DECISIONS.md` | 为什么：决策、踩过的坑 | 双方都写，只追加 | 只增不改 |
| 代码 | 做了什么 | AI 写，人验 | 跟着上面三份走 |

**铁律**：任务不是规划的唯一载体。要改结构，先改 `PLAN.md`。

## 2. 五个阶段，每个阶段一次「人拍板」

| 阶段 | 产出物 | 拍板什么 |
| --- | --- | --- |
| 1 定意图 | `PLAN.md` 的增量 | 问题定义对不对 |
| 2 拆任务 | 看板任务（每条都引用 PLAN 里的条目） | 拆法认不认 |
| 3 定结构与视觉 | 能点的最小原型 | 结构/样式行不行 |
| 4 写代码 | 可运行的改动 + 行为探针输出 | 验收 |
| 5 记结论 | `DECISIONS.md` 条目 + 记忆 | 无异议即生效 |

后端工具类功能还要满足「4 处联动」：`core/agent.py` 的 `TOOLS` 定义、executor 方法、system prompt 决策表、意图路由正则，缺一不算上线。

## 3. 与 AI 协作的硬规矩

1. **一次一题**：一轮只推进一件事，落在一个可回滚的提交上。
2. **先说清改哪里**：动代码前说明「改哪些文件、为什么」，再动手。
3. **不给证据不算完成**：必须给出行为探针输出（见 DEV_OPS.md）。改了代码 ≠ 服务已更新。
4. **原型先说假在哪**：交付最小原型时列清哪些是写死的、哪些没做（见 D-008）。
5. **需求变了先改 PLAN**：不许绕过规划直接改代码。
6. **一个概念一个名字**：范围 / 现场 / 指派 / 小块 —— 定了就别换词。
7. **不做顺手加的小功能**：想加，先写进 `PLAN.md` 的待定区。
8. **AI 说不确定的时候要信**：不确定就停下来问，不猜。

## 4. 落盘与命名

- 仓库只放代码 + 开发文档。审计日志、记忆、截图不落仓库（见 `.agent_config.yaml` 与 `.workbuddy/memory/`）。
- AI 产出的一般文件命名：`{YYYY-MM-DD}_{描述}.{ext}`；会话归档入 `docs/Agent_Audit_Logs/`。
- 固定文书用固定名：`PLAN.md`、`DECISIONS.md`、`docs/WORKFLOW.md`、`docs/DEV_OPS.md`。

## 5. 每轮结束的收尾（本项目为长期项目，强制）

1. 更新记忆：daily log + `MEMORY.md` 增量。
2. 未完成的事写进 `PLAN.md` 的待定区或任务看板，不留「口头待办」。
3. 有决策就补一条 `DECISIONS.md`。
4. 提交：本地 commit，`feat/fix/chore(scope)` 格式，不 push。
